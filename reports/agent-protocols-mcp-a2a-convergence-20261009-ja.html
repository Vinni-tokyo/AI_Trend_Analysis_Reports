規格争いは起きなかった
— MCP と A2A の役割分担

道具との接続は MCP、エージェント間の委任は A2A。その分担が組織に求めるもの
レポート作成日：2026年10月9日 | 標準レポート（5-8ページ） | データ収集：2026年10月9日

主要トレンド Top 5

本レポートの中心的な主張
MCP と A2A は競合ではなく、異なる層を受け持ちました。2026年の実務上の答えは両方を使う組み合わせであり、 その選択が終わってはじめて本当の宿題が見えてきます。本レポートは「どちらが勝つか」ではなく 「いま何を決めるべきか」に答えます。

1. 争いではなく層の分担だった — 同じ財団の傘に入った二つの規格

現状：2025年の時点では、これは規格争いとして読まれていました。しかし2026年、二つの規格は互いを押しのけませんでした。 MCP は2025年12月に Linux Foundation へ寄贈され、A2A は2026年8月17日に Agentic AI Foundation のホスティング案件となりました。二つの規格はいま同じ財団の傘の下にあります。 勝敗がついたのではなく、受け持つ層が分かれたのです。

MCP — モデルと外の世界をつなぐ

• 受け持つ層：一つのエージェントが外部のデータ・API・ファイルに届くための通り道
• 仕組み：JSON-RPC によるクライアント・サーバー構成で、道具の呼び出しと型の定まったデータのやり取り
• 出自：Anthropic が始め、公開規格へ移管
• 問い：「このエージェントは何に手が届くのか」

A2A — エージェント同士で仕事を渡す

• 受け持つ層：提供元も枠組みも異なるエージェントが相手を見つけ、仕事を委ねる
• 仕組み：HTTPS 上の JSON-RPC 2.0。発見・認証・委任をまとめて定めています
• 出自：Google が開発し Linux Foundation へ寄贈
• 問い：「このエージェントは誰に仕事を渡せるのか」

🔗 関連リンク: Model Context Protocol | A2A Protocol | Linux Foundation

展望：二つの規格が一つ屋根の下に入ったこと自体が合図です。 これからの論点は「どちらを選ぶか」ではなく「二つの層をどう噛み合わせるか」へ移っていきます。

📊 信頼性評価： 9/10
強み：Linux Foundation の公式発表、A2A の1周年発表（2026年4月9日）、Agentic AI Foundation への移管時期（2026年8月17日）がいずれも確認できます。
改善点：「争いではなかった」は結果から振り返った解釈です。2025年当時は実際に規格争いとして報じられていました。

2. 数字で見る普及 — MCP は月4億回、A2A は150組織

現状：二つの規格は広がり方の形が違います。 MCP は開発者ひとりずつに広がり、A2A は組織単位で集まりました。 MCP の月間 SDK 取得回数は、2024年11月の公開当時のおよそ200万回から2026年3月には9,700万回を超え、 共同開発者の David Soria Parra 氏は16か月で1億1,000万回に達したと述べています。 React が3年かけた節目でした。さらに2026年7月28日に状態を持たない新しい仕様が出たあと、 月4億回を超えました。今年だけで4倍です。

MCP — 生態系の厚み

• 月間 SDK 取得：2026年10月時点で4億回を突破
• 公開サーバー：2025年12月の寄贈時点で1万件超、2026年第1四半期の独立調査では17,468件を収録
• 企業への浸透：フォーチュン500の28%が MCP を導入
• 伸び方の性格：個々の開発者が自分の道具をつなぎ、下から広がりました

A2A — 参加企業の顔ぶれ

• 支持組織：2025年4月の50社ほどから2026年4月には150社超へ
• 参加企業：AWS・Cisco・Google・IBM・Microsoft・Salesforce・SAP・ServiceNow
• 稼働分野：供給網、金融、保険、IT 運用
• 本番利用：IBM・Cisco・SAP・ServiceNow が確認されています

指標の形が違うのは、狙う相手が違うからです。 MCP は一人が自分のエージェントに道具をつなげばすぐ使われます。A2A は二つの組織が合意してはじめて使われます。 前者を取得回数で、後者を参加企業数で数えるのが自然です。

🔗 関連リンク: MCP 公式文書 | A2A 1周年の発表

展望：MCP の4倍の伸びは7月の新仕様と結びついています。 つなぎ方が軽くなれば、つなげる先が増えます。一方で A2A の広がり方は、企業間の合意の速さに縛られます。

📊 信頼性評価： 7/10
強み：A2A の150組織は Linux Foundation の公式発表で確認できます。MCP の9,700万回・1億1,000万回の時点も複数の出典が一致します。
改善点：「月4億回」と公開サーバー数（15,930〜17,468）は集計主体と基準が異なるため幅があります。傾向は明らかですが、単一の数字で断定するのは早計です。

3. 2026年の実務上の答えは組み合わせ — どこに何を載せるか

現状：現場の選択はすでに定まっています。 多くの本番構成は道具の層に MCP、エージェント間の調整に A2A を併用しています。 各エージェントが自分の道具を MCP でつなぎ、そのエージェント同士が仕事を渡し合う必要があるときだけ、上に A2A を載せる形です。

下の層 — 各エージェントの内側

• データベース・ファイル・社内 API への接続 → MCP
• エージェントごとに必要な道具だけをつなぐ
• 権限はこの層で最も狭く取るのが原則です
• 変えやすい：道具を足しても引いても他のエージェントへの影響は小さく済みます

上の層 — エージェントの間

• 能力の公開・相手の発見・作業の委任 → A2A
• 提供元の異なるエージェント同士をつなぐときだけ必要
• 組織の境界を越えると認証の方式が論点になります
• 変えにくい：相手の組織との合意がかかっています

あわせて読む — 本サイトの2025年1月のレポート 「Anthropic MCP：道具の呼び出しからコード実行へのパラダイム転換」は、 四つ目の項目を「標準化競争：OpenAI の採用 vs Google の A2A 公開」と記していました。 1年9か月後、その競争は勝敗ではなく層の分担として決着しました。 あのレポートが MCP の内側の設計を扱ったとすれば、本レポートは MCP の外側の位置を扱います。

展望：組み合わせが前提になると、判断の重みは「何を使うか」から「境界をどこに引くか」へ移ります。 どの作業を一つのエージェントの中で終えるか、どこから別のエージェントへ渡すかが設計の中心になります。

📊 信頼性評価： 8/10
強み：「多くの本番構成が道具の層に MCP、エージェント間に A2A を使う」という記述は、複数の技術分析資料で一貫して確認できます。
改善点：「多く」の割合を数値で示した公開調査は見つかりませんでした。定量的な根拠ではなく業界観察に基づく記述です。

4. その他の候補 — ACP と ANP はどこにいるか

現状：規格は二つだけではありません。ただし狙う位置が少しずつ違います。 ACP（Agent Connect Protocol）は IBM と AGNTCY 連合が主導し、 エージェントのやり取りを HTTP の動詞にそのまま対応させる簡潔な方式を選びました。 作業の生成は POST、状態の確認は GET、更新は PUT、取り消しは DELETE です。 仕様が OpenAPI で記述されるため、REST を扱える道具であれば専用の開発キットなしでも接続できます。

ACP — REST 親和と中央登録所

• 方式：HTTP の動詞への直接対応、OpenAPI による仕様記述
• 発見：エージェントが能力を登録所に届け出て、利用側が問い合わせる中央登録の形
• 主導：AGNTCY 連合 — Cisco・LangChain・LlamaIndex・Galileo・Dell・Oracle・Red Hat
• 移管：2025年7月に Linux Foundation へ寄贈

そのほかの流れ

• ANP（Agent Network Protocol）：開かれた網の上でのエージェント間通信を狙う
• Matrix 系：アリババの HiClaw などで採用
• XMPP：長い歴史を持つ通信規格の再利用で、エージェント専用の設計ではありません
• 三つとも、まだ MCP・A2A ほどの普及規模には届いていません

🔗 関連リンク: AGNTCY | Linux Foundation のプロジェクト

展望：ACP の REST 親和性は既存の仕組みに載せやすいという利点がありますが、 中央登録の形は A2A の分散した発見の仕方とは設計思想が異なります。 当面は MCP と A2A の組み合わせが既定値であり、ACP は REST の資産が厚い組織での選択肢として残る見込みです。

📊 信頼性評価： 8/10
強み：ACP の設計方式（HTTP 動詞への対応・OpenAPI・中央登録所）、AGNTCY の構成企業、Linux Foundation への寄贈時期が確認できます。
改善点：ANP と Matrix 系は公開された普及指標が乏しく、位置づけのみを記述しました。比較可能な数値は示せていません。

5. 分担が済んだあとの宿題 — 認証・権限・監査の空白

現状：規格が整えば通信は片づきます。しかし「このエージェントがその仕事をしてよいのか」は残ります。 A2A は発見・認証・委任を定め、規制産業の要請を受けて認証の方式を増やしてきましたが、 規格は誰が何を許されているかを組織の代わりに決めてはくれません。 エージェントが別のエージェントへ仕事を渡すとき権限も一緒に渡るのか、監査の記録が境界を越えて続くのかは、 いまも各組織の設計しだいです。

規格が答えてくれること

• どうやって相手を見つけるか（発見）
• どんな形でやり取りするか（伝送と表現形式）
• どんな能力があると知らせるか（能力の公開）
• 相手が本物かをどう確かめるか（認証方式の枠組み）

組織が自ら決めること

• 権限の伝わり方：委任のとき権限は狭まるのか、そのまま付いていくのか
• 監査の連続性：境界を越えたあとの行動を誰が記録するのか
• 逸脱の検知：許した範囲を越えたとき何が知らせてくれるのか
• 巻き戻し：渡した仕事が誤ったとき、どこで止めるのか

あわせて読む — 本サイトの2026年10月9日のレポート 「見送られたモデルが残した基準 — GPT-6.1 Astra 中止が明らかにしたもの」は、 OpenAI が自社モデルを出さなかった理由を「与えられた権限の内側に留まる力」として整理しました。 本節の空白は、同じ問題をモデルではなく規格の層から見たものです。 一つのモデルが範囲を守るかと、複数のエージェントの間で範囲が正しく伝わるかは、一対の問いです。

展望：通信の規格が安定すると、次の標準化の圧力は権限と監査へ移ります。 委任のときに権限を狭めて渡す方法、境界を越える監査記録の形式が、次の議論の中心になる可能性が高いと見られます。

📊 信頼性評価： 7/10
強み：A2A が規制産業の要請に合わせて認証方式を広げてきた点は確認できます。規格と権限設計が別の問題だという切り分けも技術文書と一致します。
改善点：「権限・監査が次の標準化の対象になる」という見通しは本分析の判断です。具体的な標準化作業が進行中だという公開の根拠は確認できていません。

競争環境と市場ポジショニング

規格の層による4層構造

エージェントの仕組みを立てるとき決めるべき層は四つです。下へ行くほど変えやすく、上へ行くほど引き返す費用が大きくなります。 （本分析による分類です。）

層 決める内容 代表的な選択肢 引き返す費用
第1層 — 道具との接続 エージェントがデータ・API・ファイルに届く通り道 MCP 低い — 道具ごとに足し引きできます
第2層 — 内部の調整 同じ組織の中でエージェント同士の作業を振り分ける 枠組み自体の機能、または A2A 中程度 — 内部の設計変更で吸収できます
第3層 — 組織をまたぐ委任 提供元や会社の異なるエージェントへ仕事を渡す A2A（一部 ACP） 高い — 相手の組織との合意がかかります
第4層 — 権限と監査 誰が何を許され、何が記録されるか 規格なし — 組織が自ら設計 非常に高い — 事故のあとで変えるのでは遅い

MCP 月間 SDK 取得回数の伸び

出典：複数の公開集計。集計主体によって幅があるため、時点ごとの代表値を用いています。

  • 規格争いが層の分担として決着しました：MCP と A2A が同じ財団の傘に入りました。
  • 普及指標の性格が分かれます：MCP は取得回数で、A2A は参加企業数で数えるのが自然です。
  • 軽い仕様が普及を押し上げました：2026年7月の新仕様のあと、MCP の月間取得が4倍になりました。
  • 主要クラウド3社がすべて A2A を取り込みました：AWS・Google・Microsoft が揃い、事実上の伝送規格になりました。
  • 次の空白は権限と監査です：通信は規格化されましたが、「してよいか」は依然として組織の仕事です。

重要なポイント

  • 普及の規模が異なります：MCP は月間 SDK 取得が4億回を超えフォーチュン500の28%が導入、A2A は支持組織が150社を超えました。
  • 実務上の答えはすでに出ています：道具との接続は MCP、エージェント間の委任は A2A という組み合わせが既定値です。
  • 引き返す費用は層ごとに違います：道具との接続は変えやすい一方、組織をまたぐ委任は相手との合意がかかるため慎重さが要ります。

状況別の参考

これからエージェントを作り始める組織 → MCP から
理由：道具との接続は引き返す費用が最も小さく、生態系が厚いためつなげる先が多くあります。
複数チームのエージェントをつなぐ組織 → 境界の設計から
理由：A2A を載せる前に、どこまで一つのエージェントの中で終えるかを決める必要があります。境界を後から変えると費用がかさみます。
規制産業にある組織 → 第4層（権限・監査）から
理由：規格が答えてくれない領域であり、事故のあとに設計するのでは遅いためです。

総合評価：肯定。規格が分裂せず層として整理されたことは導入する組織にとって有利です。ただし通信の規格化が済んだからといって権限の問題まで解決したわけではない、という点は明確にしておく必要があります。

主要用語の説明

MCP（Model Context Protocol） — AI モデルを外部のデータ・API・ファイルにつなぐための規格です。差込口の規格にたとえると、どんな道具でも同じ形で挿せるようにするものです。
A2A（Agent2Agent） — 異なる会社や枠組みで作られたエージェントが、相手を見つけ、身元を確かめ、仕事を渡せるようにする規格です。
ACP（Agent Connect Protocol） — IBM と AGNTCY 連合が主導する規格で、エージェントのやり取りを HTTP の動詞（POST・GET・PUT・DELETE）にそのまま対応させます。
JSON-RPC — プログラム同士が「この機能をこの値で実行してほしい」と頼むための簡単な取り決めです。MCP と A2A の両方がこの方式を使っています。
状態を持たない設計 — サーバーが以前のやり取りを覚えず、要求のたびに必要な情報をすべて受け取る方式です。接続が軽くなり、規模を広げやすくなります。
能力の公開 — エージェントが「自分はこういう仕事ができる」と知らせることです。相手が仕事を渡すかどうかを判断する手がかりになります。
Agentic AI Foundation — 自律エージェント関連の規格を扱うために Linux Foundation の下に作られた財団です。MCP と A2A の両方がここに属しています。
