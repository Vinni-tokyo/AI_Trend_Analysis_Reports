프로토콜 전쟁은 없었다
— MCP 와 A2A 의 역할 분담

도구 연결은 MCP, 에이전트 간 위임은 A2A. 그 분담이 조직에 요구하는 것
보고서 작성일: 2026년 10월 9일 | 표준 보고서 (5-8페이지) | 데이터 수집: 2026년 10월 9일

주요 트렌드 Top 5

이 보고서의 중심 주장
MCP 와 A2A 는 경쟁자가 아니라 서로 다른 층을 맡았습니다. 2026년의 실무 해법은 둘 다 쓰는 하이브리드이며, 그 선택이 끝난 뒤에야 진짜 숙제가 드러납니다. 이 글은 「어느 쪽이 이기나」가 아니라 「무엇을 지금 결정해야 하나」에 답합니다.

1. 경쟁이 아니라 층 분담이었다 — 같은 재단 아래로 들어간 두 프로토콜

현황: 2025년만 해도 이것은 표준 경쟁으로 읽혔습니다. 그러나 2026년에 두 프로토콜은 서로를 밀어내지 않았습니다. MCP는 2025년 12월 Linux Foundation 에 기증됐고, A2A는 2026년 8월 17일 Agentic AI Foundation 의 호스팅 프로젝트가 됐습니다. 두 프로토콜은 지금 같은 재단 우산 아래에 있습니다. 승부가 난 것이 아니라, 맡는 층이 갈린 것입니다.

MCP — 모델과 바깥세상을 잇는다

• 맡는 층: 하나의 에이전트가 외부 데이터·API·파일시스템에 닿는 통로
• 방식: JSON-RPC 기반 클라이언트–서버 구조로 도구 호출과 형식이 정해진 데이터 교환
• 주도: Anthropic 이 시작해 공개 표준으로 이관
• 질문: 「이 에이전트는 무엇에 접근할 수 있는가」

A2A — 에이전트끼리 일을 넘긴다

• 맡는 층: 서로 다른 벤더·프레임워크의 에이전트가 상대를 발견하고 일을 위임
• 방식: HTTPS 위의 JSON-RPC 2.0. 발견·인증·위임을 함께 규정
• 주도: Google 이 개발해 Linux Foundation 에 기증
• 질문: 「이 에이전트는 누구에게 일을 넘길 수 있는가」

🔗 관련 링크: Model Context Protocol | A2A Protocol | Linux Foundation

전망: 두 프로토콜이 한 지붕 아래 들어갔다는 사실 자체가 신호입니다. 앞으로의 논점은 「무엇을 고를까」가 아니라 「두 층을 어떻게 맞물릴까」로 옮겨갑니다.

📊 신뢰도 평가: 9/10
강점: Linux Foundation 공식 발표와 A2A 1주년 보도자료(2026-04-09), Agentic AI Foundation 편입 시점(2026-08-17)이 모두 확인됩니다.
개선점: 「경쟁이 아니었다」는 결과론적 해석입니다. 2025년 시점에는 실제로 경쟁 구도로 보도된 바 있습니다.

2. 숫자로 본 채택 — MCP 월 4억 다운로드, A2A 150개 조직

현황: 두 프로토콜의 채택 속도는 성격이 다릅니다. MCP 는 개발자 단위로 번졌고, A2A 는 기업 단위로 모였습니다. MCP 의 월간 SDK 내려받기는 2024년 11월 공개 당시 약 200만에서 2026년 3월 9,700만을 넘었고, 공동 개발자 David Soria Parra 는 16개월 만에 1억 1,000만에 도달했다고 밝혔습니다. React 가 3년 걸린 이정표였습니다. 그리고 2026년 7월 28일 상태를 두지 않는(stateless) 새 명세가 나온 뒤 월 4억을 넘어섰습니다. 올해만 네 배입니다.

MCP — 생태계의 두께

• 월간 SDK 내려받기: 2026년 10월 기준 4억 돌파
• 공개 서버: 2025년 12월 1만 개 이상 → 2026년 1분기 독립 조사에서 17,468개 색인
• 기업 침투: 포춘 500 기업의 28%가 MCP 를 배포
• 성장의 성격: 개별 개발자가 각자의 도구를 연결하며 바닥부터 번졌습니다

A2A — 참여 기업의 면면

• 지지 조직: 2025년 4월 50여 곳 → 2026년 4월 150곳 초과
• 참여 기업: AWS·Cisco·Google·IBM·Microsoft·Salesforce·SAP·ServiceNow
• 실가동 영역: 공급망, 금융, 보험, IT 운영
• 프로덕션 사용자: IBM·Cisco·SAP·ServiceNow 가 확인됩니다

숫자의 모양이 다른 이유는 겨냥하는 대상이 다르기 때문입니다. MCP 는 한 사람이 자기 에이전트에 도구를 붙이면 곧바로 쓰입니다. A2A 는 조직 두 곳이 합의해야 쓰입니다. 전자는 내려받기로, 후자는 참여 기업 수로 세는 것이 자연스럽습니다.

🔗 관련 링크: MCP 공식 문서 | A2A 1주년 발표

전망: MCP 의 네 배 성장은 7월의 stateless 명세와 맞물려 있습니다. 연결 방식이 가벼워지면 붙일 수 있는 곳이 늘어납니다. 반면 A2A 의 확산 속도는 기업 간 합의 속도에 묶입니다.

📊 신뢰도 평가: 7/10
강점: A2A 150개 조직은 Linux Foundation 공식 보도자료로 확인됩니다. MCP 의 9,700만·1억 1,000만 시점도 복수 출처가 일치합니다.
개선점: 「월 4억」과 공개 서버 수(15,930~17,468)는 집계 주체와 기준이 서로 달라 편차가 있습니다. 추세는 분명하나 단일 숫자로 단정하기는 이릅니다.

3. 2026년 실무 해법은 하이브리드 — 어디에 무엇을 얹는가

현황: 현장의 선택은 이미 정해졌습니다. 대부분의 프로덕션 에이전트 구성은 도구 층에 MCP, 에이전트 간 조율에 A2A 를 함께 씁니다. 각 에이전트는 자기 도구를 MCP 로 붙이고, 그 에이전트들이 서로 일을 넘겨야 할 때만 위에 A2A 를 얹는 구조입니다.

아래층 — 각 에이전트 안쪽

• 데이터베이스·파일·사내 API 연결 → MCP
• 에이전트마다 필요한 도구만 붙임
• 권한은 이 층에서 가장 좁게 잡는 것이 원칙
• 바꾸기 쉬움: 도구를 더하거나 빼도 다른 에이전트에 영향이 적습니다

위층 — 에이전트 사이

• 역량 공개·상대 발견·작업 위임 → A2A
• 벤더가 다른 에이전트끼리 붙일 때만 필요
• 조직 경계를 넘을 때 인증 방식이 쟁점이 됩니다
• 바꾸기 어려움: 상대 조직과의 합의가 걸려 있습니다

이어 읽기 — 본 사이트의 2025년 1월 보고서 「앤트로픽 MCP: 도구 호출에서 코드 실행으로의 패러다임 전환」은 네 번째 꼭지를 「표준화 경쟁: OpenAI 채택 vs Google A2A 출시」로 적었습니다. 1년 9개월 뒤, 그 경쟁은 승패가 아니라 층 분담으로 끝났습니다. 그 글이 MCP 안쪽의 설계를 다뤘다면, 이 글은 MCP 바깥의 자리를 다룹니다.

전망: 하이브리드가 기본이 되면 선택의 무게는 「무엇을 쓸까」에서 「경계를 어디에 그을까」로 옮겨갑니다. 어떤 작업을 한 에이전트 안에서 끝낼지, 어디부터 다른 에이전트에 넘길지가 설계의 핵심이 됩니다.

📊 신뢰도 평가: 8/10
강점: 「대부분의 프로덕션 스택이 도구 층에 MCP, 에이전트 간에 A2A 를 쓴다」는 서술은 복수의 기술 분석 자료에서 일관되게 확인됩니다.
개선점: 「대부분」의 비율을 수치로 제시한 공개 조사는 찾지 못했습니다. 정량 근거가 아니라 업계 관찰에 기반한 서술입니다.

4. 그 외 후보들 — ACP·ANP 는 어디에 있나

현황: 두 프로토콜만 있는 것은 아닙니다. 다만 겨냥하는 자리가 조금씩 다릅니다. ACP(Agent Connect Protocol) 는 IBM 과 AGNTCY 연합이 주도하며, 에이전트 상호작용을 HTTP 동사에 그대로 대응시키는 간결한 방식을 택했습니다. 작업 생성은 POST, 상태 확인은 GET, 갱신은 PUT, 취소는 DELETE 입니다. 명세가 OpenAPI 로 기술되므로 REST 를 다룰 수 있는 도구라면 전용 SDK 없이도 접근할 수 있습니다.

ACP — REST 친화와 중앙 레지스트리

• 방식: HTTP 동사에 직접 대응, OpenAPI 명세
• 발견: 에이전트가 역량을 디렉터리 서비스에 등록하고 클라이언트가 조회하는 중앙 레지스트리 모형
• 주도: AGNTCY 연합 — Cisco·LangChain·LlamaIndex·Galileo·Dell·Oracle·Red Hat
• 이관: 2025년 7월 Linux Foundation 에 기증

그 밖의 흐름

• ANP(Agent Network Protocol): 개방형 네트워크에서의 에이전트 간 통신을 겨냥
• Matrix 계열: 알리바바의 HiClaw 등에서 채택
• XMPP: 메시징 표준을 재활용하는 접근으로, 역사가 길지만 에이전트 전용 설계는 아닙니다
• 세 갈래 모두 아직 MCP·A2A 만큼의 채택 규모에는 이르지 못했습니다

🔗 관련 링크: AGNTCY | Linux Foundation 프로젝트

전망: ACP 의 REST 친화성은 기존 시스템에 얹기 좋다는 장점이 있지만, 중앙 레지스트리 모형은 A2A 의 분산 발견 방식과 설계 철학이 다릅니다. 당분간은 MCP·A2A 조합이 기본값이고, ACP 는 REST 자산이 두터운 조직에서 선택지로 남을 가능성이 큽니다.

📊 신뢰도 평가: 8/10
강점: ACP 의 설계 방식(HTTP 동사 대응·OpenAPI·중앙 레지스트리)과 AGNTCY 구성 기업, Linux Foundation 기증 시점이 확인됩니다.
개선점: ANP 와 Matrix 계열은 공개 채택 지표가 부족해 위치만 서술했습니다. 비교 가능한 수치를 제시하지 못했습니다.

5. 분담이 끝난 뒤 남은 숙제 — 인증·권한·감사의 공백

현황: 프로토콜이 정리되면 통신은 해결됩니다. 그러나 「이 에이전트가 그 일을 해도 되는가」는 남습니다. A2A 는 발견·인증·위임을 규정하고 규제 산업의 요구를 반영해 인증 방식을 추가해 왔지만, 프로토콜은 누가 무엇을 허가받았는지를 조직 대신 정해 주지 않습니다. 에이전트가 다른 에이전트에 일을 넘길 때 권한이 함께 넘어가는지, 감사 기록이 경계를 넘어 이어지는지는 여전히 각 조직의 설계에 달려 있습니다.

프로토콜이 답해 주는 것

• 어떻게 상대를 찾는가 (발견)
• 어떤 형식으로 주고받는가 (전송·직렬화)
• 어떤 역량을 가졌다고 알리는가 (역량 광고)
• 상대가 진짜인지 어떻게 확인하는가 (인증 방식의 틀)

조직이 직접 정해야 하는 것

• 권한의 전파: 위임할 때 권한이 좁아지는가, 그대로 따라가는가
• 감사의 연속성: 경계를 넘은 뒤의 행동을 누가 기록하는가
• 범위 이탈 탐지: 허락한 범위를 넘었을 때 무엇이 알려 주는가
• 되돌리기: 넘긴 일이 잘못됐을 때 어디서 멈추는가

이어 읽기 — 본 사이트의 2026년 10월 9일 보고서 「접힌 모델이 남긴 기준 — GPT-6.1 Astra 철회가 드러낸 것」은 OpenAI 가 자사 모델을 내보내지 않은 이유를 「권한 안에 머무는 능력」으로 정리했습니다. 이 절의 공백은 같은 문제를 모델이 아니라 프로토콜 층에서 본 것입니다. 한 모델이 범위를 지키는가와, 여러 에이전트 사이에서 범위가 전달되는가는 한 쌍의 질문입니다.

전망: 통신 표준이 안정되면 다음 표준화 압력은 권한과 감사로 옮겨갑니다. 위임 시 권한을 좁혀 넘기는 방식, 경계를 넘는 감사 기록의 형식이 다음 논의의 중심이 될 가능성이 높습니다.

📊 신뢰도 평가: 7/10
강점: A2A 가 규제 산업의 요구에 맞춰 인증 방식을 확장해 왔다는 점은 확인됩니다. 프로토콜과 권한 설계가 분리된 문제라는 구분도 기술 문서와 일치합니다.
개선점: 「권한·감사가 다음 표준화 대상이 된다」는 전망은 본 분석의 판단입니다. 구체적 표준화 작업이 진행 중이라는 공개 근거는 확인하지 못했습니다.

경쟁 환경과 시장 포지셔닝

프로토콜 층의 4계층 구조

에이전트 시스템을 세울 때 결정해야 하는 층은 넷입니다. 아래로 갈수록 바꾸기 쉽고, 위로 갈수록 되돌리기 비용이 큽니다. (본 분석에 따른 분류입니다.)

층 결정 내용 대표 선택지 되돌리기 비용
1층 — 도구 연결 에이전트가 데이터·API·파일에 닿는 통로 MCP 낮음 — 도구 단위로 더하고 뺄 수 있습니다
2층 — 내부 조율 같은 조직 안 에이전트들의 작업 분배 프레임워크 자체 기능 또는 A2A 중간 — 내부 설계 변경으로 감당 가능합니다
3층 — 조직 간 위임 다른 벤더·다른 회사의 에이전트에 일을 넘김 A2A (일부 ACP) 높음 — 상대 조직과의 합의가 걸립니다
4층 — 권한·감사 누가 무엇을 허가받았고 무엇이 기록되는가 표준 부재 — 조직이 직접 설계 매우 높음 — 사고가 난 뒤 바꾸면 늦습니다

MCP 월간 SDK 내려받기의 성장

출처: 복수의 공개 집계. 집계 주체에 따라 편차가 있어 시점별 대표값을 사용했습니다.

프로토콜 비교

본 분석에 따른 상대 평가입니다. 다섯 축은 각 프로토콜이 규정하는 범위와 현재 채택 규모를 기준으로 했습니다.

시장 변화 다섯 가지

  • 표준 경쟁이 층 분담으로 끝났습니다: MCP 와 A2A 가 같은 재단 우산 아래 들어갔습니다.
  • 채택 지표의 성격이 갈립니다: MCP 는 내려받기로, A2A 는 참여 기업 수로 세는 것이 자연스럽습니다.
  • 가벼운 명세가 확산을 키웁니다: 2026년 7월 stateless 명세 이후 MCP 의 월간 내려받기가 네 배가 됐습니다.
  • 클라우드 3사가 모두 A2A 를 품었습니다: AWS·Google·Microsoft 가 함께 참여하며 사실상의 전송 표준이 됐습니다.
  • 다음 공백은 권한과 감사입니다: 통신은 표준화됐지만 「해도 되는가」는 여전히 조직의 몫입니다.

활용 아이디어

시장에서 관찰되는 주요 활용 접근을 소개합니다.

1. 층별 현황 정리 - 운영 중인 에이전트를 도구 연결·내부 조율·조직 간 위임 세 층으로 나누어 지금 무엇을 쓰고 있는지 한 장에 적기

2. 경계 설계 선행 - A2A 도입 전에 어떤 작업을 한 에이전트 안에서 끝낼지 경계를 먼저 그어 되돌리기 비용이 큰 결정을 뒤로 미루기

3. 권한 전파 점검 - 에이전트가 다른 에이전트에 일을 넘길 때 권한이 좁아지는지, 감사 기록이 경계를 넘어 이어지는지 확인

경영진 요약

핵심 발견

  • 경쟁이 아니라 분담이었습니다: MCP 는 2025년 12월, A2A 는 2026년 8월에 각각 Linux Foundation 계열 재단으로 들어가 같은 우산 아래 놓였습니다.
  • 채택 규모가 다릅니다: MCP 는 월간 SDK 내려받기가 4억을 넘었고 포춘 500 의 28%가 배포했으며, A2A 는 지지 조직이 150곳을 넘었습니다.
  • 실무 해법은 이미 정해졌습니다: 도구 연결은 MCP, 에이전트 간 위임은 A2A 를 함께 쓰는 하이브리드가 기본값입니다.
  • 되돌리기 비용이 층마다 다릅니다: 도구 연결은 바꾸기 쉽지만 조직 간 위임은 상대와의 합의가 걸려 있어 신중해야 합니다.
  • 다음 공백은 권한과 감사입니다: 프로토콜은 통신을 규정하지만, 위임할 때 권한이 어떻게 전파되고 감사가 어떻게 이어지는지는 조직이 설계해야 합니다.

상황별 참고

이제 막 에이전트를 만들기 시작한 조직 → MCP 부터
이유: 도구 연결은 되돌리기 비용이 가장 낮고, 생태계가 두터워 붙일 수 있는 것이 많습니다.
여러 팀의 에이전트를 묶어야 하는 조직 → 경계 설계 먼저
이유: A2A 를 얹기 전에 어디까지 한 에이전트 안에서 끝낼지 정해야 합니다. 경계를 늦게 바꾸면 비용이 큽니다.
규제 산업에 있는 조직 → 4층(권한·감사)부터
이유: 프로토콜이 답해 주지 않는 영역이며, 사고가 난 뒤에 설계하면 늦습니다.

종합 평가: 긍정 (표준이 갈라지지 않고 층으로 나뉘어 정리된 것은 도입 조직에게 유리합니다. 다만 통신 표준화가 끝났다고 해서 권한 문제까지 해결된 것은 아니라는 점을 분명히 할 필요가 있습니다.)

📋 종합 신뢰도 평가

7.8/10

종합 평가: Linux Foundation 공식 발표와 1주년 보도자료 등 1차 자료를 중심으로 확인했으며, 채택 수치는 복수 출처를 대조했습니다.

주요 강점: A2A 의 참여 조직 수, 재단 편입 시점, 참여 기업 명단이 공식 자료로 확인됩니다. 두 프로토콜의 역할 구분이 기술 문서와 일치합니다.

개선 우선순위: ① MCP 의 월간 내려받기 수치는 집계 주체별 편차가 큽니다(9,700만~4억). 추세는 분명하나 단일 수치로 단정하기 어렵습니다. ② 「대부분의 프로덕션 스택이 하이브리드」라는 서술의 정량 근거는 확인하지 못했습니다. ③ 4계층 분류와 되돌리기 비용 평가는 저자의 제안입니다.

주요 용어 설명

MCP(Model Context Protocol) — AI 모델을 외부 데이터·API·파일시스템에 연결하는 표준입니다. 콘센트 규격에 비유하면, 어떤 도구든 같은 모양으로 꽂을 수 있게 해 줍니다.
A2A(Agent2Agent) — 서로 다른 회사·프레임워크에서 만든 에이전트가 상대를 찾고, 신원을 확인하고, 일을 넘길 수 있게 하는 표준입니다.
ACP(Agent Connect Protocol) — IBM 과 AGNTCY 연합이 주도하는 표준으로, 에이전트 상호작용을 HTTP 동사(POST·GET·PUT·DELETE)에 그대로 대응시킵니다.
JSON-RPC — 프로그램끼리 「이 기능을 이 값으로 실행해 달라」고 요청하는 간단한 약속입니다. MCP 와 A2A 가 모두 이 방식을 씁니다.
상태를 두지 않는(stateless) 설계 — 서버가 이전 대화를 기억하지 않고 요청마다 필요한 정보를 모두 받는 방식입니다. 연결이 가벼워져 확장이 쉬워집니다.
역량 광고(Capability Advertisement) — 에이전트가 「나는 이런 일을 할 수 있다」고 공개하는 것입니다. 상대가 일을 넘길지 판단하는 근거가 됩니다.
Agentic AI Foundation — 자율 에이전트 관련 표준을 다루기 위해 Linux Foundation 아래 만들어진 재단입니다. MCP 와 A2A 가 모두 이곳에 속해 있습니다.
