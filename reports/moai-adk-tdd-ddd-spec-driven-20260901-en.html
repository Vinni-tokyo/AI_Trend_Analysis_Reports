MoAI-ADK and Spec-Driven Development:
The Return of TDD and DDD

Why old methodologies became necessary again once AI started writing the code
Report date: September 1, 2026 | Standard report (5–8 pages)

Top 5 Trends

1. Spec-driven development went mainstream in 2026

Where things stand: The reason spec-driven development (SDD) went mainstream in 2026 is blunt — AI agents are great at writing code and terrible at guessing what you meant. SDD is the practice of writing a structured, versioned specification before invoking a coding agent, so the agent receives explicit goals, constraints and acceptance criteria. It emerged as a direct response to the failure mode of "vibe coding": agents that produce plausible code which drifts from intent, hallucinates APIs, and decays as projects scale.

How it differs from TDD and BDD

• TDD: "write the test first"
• BDD: "write the behaviour first, in business language"
• SDD: "write the whole spec first — behaviour, architecture, edge cases, constraints — and let an agent produce the code, tests and docs"
• Scope difference: unit tests verify functions; they do not catch architectural violations or API contract drift

The 2026 tooling landscape

• Every major tool now ships SDD: GitHub Spec Kit · AWS Kiro · Claude Code · Cursor · OpenSpec · BMAD · Tessl · Google Antigravity
• Independent evaluation (Feb 2026): 13 scoring categories on a medium-sized serverless Python backend — OpenSpec scored highest overall
• But rankings shift with priorities: OpenSpec suits teams valuing change accountability; others fit living-spec synchronisation better

Outlook: There is no single "best" tool — the stack and your priorities decide. Tools separate along two axes: how much they do for you, and whether they verify the result.

2. MoAI-ADK — completion judged by evidence, not by claim

Where things stand: MoAI-ADK is a verification-driven orchestration framework that wraps Claude Code to enforce structured code generation. Its design premise is explicit: rather than accepting agent claims at face value, the system binds every completion assertion to independently verified evidence — test output, coverage metrics, lint results. It ships as a single Go binary with zero dependencies and currently sits at 1.2k GitHub stars, 222 forks and 4,456 commits.

Plan → Run → Sync

• Plan: SPEC authoring using GEARS-format requirements
• Run: TDD (RED→GREEN→REFACTOR) or DDD (ANALYZE→PRESERVE→IMPROVE)
• Automatic selection: new projects or coverage above 10% trigger TDD; legacy codebases under 10% use DDD
• Sync: documentation and pull-request creation

TRUST 5 quality gates

• The acronym: Tested · Readable · Unified · Secured · Trackable
• Execution: lint, format, type-checking and tests run concurrently
• Four scoring dimensions: functionality 40% · security 25% · craft 20% · consistency 15%
• Twelve agents: manager, evaluator, builder and advisor roles — including independent auditors that prevent bias

Outlook: This answers "how do I trust AI-written code?" through evidence binding rather than process. Notably, its 16 languages (Go, Python, TypeScript, Rust, Java, Kotlin, C#, Ruby, PHP, Elixir, C++, Scala, R, Flutter, Swift, JavaScript) receive equal treatment via marker-based detection rather than preferential support.

3. TDD's return — one of the few brakes on AI regression

Where things stand: Adoption of AI coding tools widened while trust moved the other way. 84% of developers use or plan to use AI tools (up from 76% in 2024) and 51% use them daily, yet trust in AI accuracy fell from 40% to 29%, an 11-point drop. Meanwhile reviewing AI-generated code became the single largest time sink at a median 11.4 hours per week.

Quality indicators moving the wrong way

• More bugs: 52% report bug volume has increased since adopting AI
• PR defects: roughly 1.7× more issues found in AI-coauthored PRs (CodeRabbit, Dec 2025)
• Code duplication up 4×, with rising short-term churn — more copy/paste, less maintainable design
• Even so: 75% still manually review every AI-generated snippet before merging

A measured remedy — TDAD

• Problem: AI coding agents frequently break previously passing tests
• Method: graph-based pre-change impact analysis
• Result: regression rate 6.08% → 1.82% (a 70% reduction)
• Scale: 100 SWE-bench Verified instances (arXiv, 2026)

🔗 Related Links: TDAD: Test-Driven Agentic Development (arXiv) | CodeRabbit | Stack Overflow Developer Survey

Outlook: TDD has shifted from "good practice" to "necessary safety device". Once code is produced faster than humans can read it, tests are the only verification method that scales.

📊 Credibility Assessment:8.5/10
Strengths: Quantitative arXiv results (6.08%→1.82%, N=100) presented alongside survey figures; the trust decline (40%→29%) is a year-over-year comparison
Weaknesses: Survey sample sizes and sponsoring bodies were confirmed through secondary aggregators; cross-checking the original reports is warranted

4. DDD matters more, not less, now that AI writes the code

Where things stand: Domain-driven design is being re-read as the frame that turns agentic coding from "prompt spaghetti" into maintainable engineering. The core move is to carry DDD's three instruments straight into agent design: bounded contexts become agent responsibility boundaries, the ubiquitous language becomes the consistency contract for tool inputs and outputs, and the context map makes integration points explicit.

Applied to multi-agent systems

• One agent = one bounded context: the agent encapsulates the knowledge and rules of its domain
• Example: an inventory management agent is solely responsible for inventory interactions
• Effect: responsibility boundaries are defined by structure, not by prompt wording
• Integration points: made explicit in the context map, preventing implicit coupling

AI assists boundary discovery

• Role: to support rather than replace boundary identification
• Method: analysing source code, database schemas and interaction patterns to surface signals of domain cohesion and separation
• The pragmatic 2026 view: start from team boundaries and organisational structure, not purely technical analysis
• MoAI-ADK example: assigns the DDD cycle (ANALYZE-PRESERVE-IMPROVE) automatically to legacy code under 10% coverage

Outlook: The more code AI produces, the more valuable it becomes for a human to decide in advance where a module's responsibility ends. Absent a boundary, agents do not create one — they cross it.

📊 Credibility Assessment:7.5/10
Strengths: Conference talks and practitioner engineering blogs independently propose the same mapping (bounded context = agent boundary)

5. The modular monolith returns — cost is now the primary constraint

Where things stand: According to the CNCF Q1 2026 report, 42% of organisations that initially adopted microservices have consolidated some services into larger deployable units — that is, back into modular monoliths. Internal measurements published in April 2026 report that after adopting pack-based modularisation, new-developer onboarding time fell by 55% and cross-module regressions dropped 68% year-over-year.

A maturing toolchain

• All landed in Q1 2026: Spring Modulith 1.4 GA · ArchUnit 1.3 · jMolecules 2026.0
• Significance: the evolutionary architecture toolchain has reached maturity
• Fitness functions: architectural rules enforced as tests
• Event sourcing: production-grade stores such as Ecotone and EventSourcingDB now available

Why the reversal now

• Cost is the primary constraint: in 2026 architecture decisions are bounded by cost rather than scalability
• Correction after over-application: more than 90% of enterprise projects are adequately served by a well-designed modular monolith
• AI reinforces it: the rise of LLM-integrated applications and agentic AI systems strengthens the return
• Lower barrier: adopting event sourcing moved from "years of experience" to "weeks of guided implementation"

🔗 Related Links: Spring Modulith | ArchUnit | jMolecules | CNCF

Outlook: DDD's module boundaries and the modular monolith's deployment unit are converging again. "Logical boundaries, single deployment" is becoming the 2026 default.

Strengths: Cites the CNCF quarterly report, an industry-standard source; the tool releases (Spring Modulith 1.4, ArchUnit 1.3) are verifiable facts
Weaknesses: The 55% onboarding and 68% regression figures come from an anonymous organisation's internal measurement and do not generalise; "more than 90%" is a qualitative judgement

Application Ideas

Approaches observed in the market.

1. Spec-first pilot - pick one feature, write the spec before handing it to an agent, and compare rework volume against the usual approach

2. Coverage-based branching - apply TDD to new modules and a DDD cycle to low-coverage legacy code

3. Deploy fitness functions - encode module boundary rules as ArchUnit-style tests to block boundary violations in AI-generated code

Executive Summary

Key findings

  • The more AI writes, the more old methodologies matter: SDD, TDD and DDD are not a nostalgia cycle — they became necessary instruments for handling code produced faster than humans can read it.
  • Adoption widened while trust narrowed: 84% of developers use AI tools, yet trust in accuracy fell from 40% to 29%, and review became the largest time sink at 11.4 hours per week.
  • Regression is measurable and reducible: graph-based impact analysis cut AI agents' test regression rate from 6.08% to 1.82% (N=100).
  • Verification is where tools differentiate: approaches like MoAI-ADK bind completion claims to evidence — not "it's done" but "the tests, coverage and lint say so".
  • Architecture is contracting: 42% of microservice adopters have consolidated, and cost has overtaken scalability as the primary constraint.

Reference points by situation

Teams that want to choose their own model and agent → bolt-on CLI (Spec Kit, OpenSpec)
Rationale: it layers onto an existing workflow and avoids model lock-in.
Teams that must treat quality as a commitment → orchestration harness (MoAI-ADK, BMAD)
Rationale: quality gates and independent audit are built in, so "done" exists as code.
Organisations weighted toward legacy → DDD cycle plus fitness functions
Rationale: forcing TDD onto low-coverage code stalls progress; preserving behaviour comes first.

Overall sentiment: Positive — methodology and tooling are maturing quickly. Quality indicators are still deteriorating, however, and the gap is widening between teams with a verification regime and teams without one.

Key Terminology

SDD (Spec-Driven Development) - Writing a structured specification covering behaviour, architecture, edge cases and constraints before invoking an AI coding agent.
TDD (Test-Driven Development) - The cycle of writing a failing test (RED), making it pass (GREEN), then improving the structure (REFACTOR).
DDD (Domain-Driven Design) - Designing code structure around the language and boundaries of the business domain. In MoAI-ADK it also names the legacy-oriented ANALYZE-PRESERVE-IMPROVE cycle.
Bounded Context - The boundary within which one model and vocabulary hold consistently. In multi-agent systems it maps to a single agent's scope of responsibility.
Ubiquitous Language - The shared vocabulary used identically by developers and domain experts; also used as the contract for agent tool inputs and outputs.
Fitness Function - A mechanism that enforces architectural rules (for example, "module A must not reference B directly") as automated tests.
Modular Monolith - An architecture divided internally by module boundaries but deployed as a single unit, keeping boundaries while avoiding microservice operating costs.
Vibe Coding - Producing code through conversation alone, without a specification. The critique of its drift from intent is what gave rise to SDD.
