MoAI-ADK와 사양 주도 개발:
TDD와 DDD의 재부상

AI가 코드를 쓰는 시대에 오래된 방법론이 다시 필요해진 이유
보고서 작성일: 2026년 9월 1일 | 표준 보고서 (5-8페이지)

주요 트렌드 Top 5

1. 사양 주도 개발(SDD)이 2026년 주류가 됐다

현황: 2026년 사양 주도 개발이 주류로 올라선 이유는 단순합니다 — AI 에이전트는 코드를 잘 쓰지만, 당신이 무엇을 의도했는지 추측하는 데는 형편없기 때문입니다. SDD 는 AI 코딩 에이전트를 호출하기 전에 구조화되고 버전 관리되는 사양을 작성해, 에이전트에게 목표·제약·수용 기준을 명시적으로 주는 방식입니다. 2025년 「바이브 코딩」의 실패 양식 — 그럴듯하지만 의도에서 표류하고, API를 지어내며, 프로젝트가 커질수록 부패하는 코드 — 에 대한 직접적인 대응으로 등장했습니다.

TDD·BDD 와의 차이

• TDD: "테스트를 먼저 써라"
• BDD: "행동을 비즈니스 언어로 먼저 써라"
• SDD: "행동·아키텍처·엣지 케이스·제약을 전부 먼저 쓰고, 에이전트가 코드·테스트·문서를 생성하게 하라"
• 범위 차이: 단위 테스트는 함수를 검증할 뿐, 아키텍처 위반이나 API 계약 표류는 못 잡는다

2026년 도구 지형

• 주요 도구 전부 SDD 탑재: GitHub Spec Kit · AWS Kiro · Claude Code · Cursor · OpenSpec · BMAD · Tessl · Google Antigravity
• 독립 평가(2026-02): 중간 규모 서버리스 Python 백엔드에서 13개 항목 채점 — OpenSpec 종합 1위
• 단, 우선순위가 바뀌면 순위도 바뀐다: 변경 이력·문서 추적을 중시하면 OpenSpec, 살아있는 사양 동기화를 중시하면 다른 선택

🔗 관련 링크: GitHub Spec Kit | AWS Kiro | Tessl | spec-compare

전망: 「최고의 도구」는 없고 스택과 우선순위가 선택을 정합니다. 도구들은 두 축에서 갈립니다 — 얼마나 대신 해주는가, 그리고 결과를 검증하는가.

📊 신뢰도 평가:8.5/10
강점: 복수의 독립 가이드가 동일한 도구 목록과 SDD/TDD 구분을 제시 · 2026-02 독립 평가는 채점 항목 수(13개)까지 명시
개선점: "주류가 됐다"는 채택률 통계가 아니라 도구 출시 현황에 근거한 판단

2. MoAI-ADK — 주장이 아니라 증거로 완료를 판정한다

현황: MoAI-ADK 는 Claude Code 를 감싸 구조화된 코드 생성을 강제하는 검증 주도 오케스트레이션 프레임워크입니다. 핵심 설계 철학은 명확합니다 — 에이전트의 완료 주장을 액면가로 받아들이지 않고, 모든 완료 선언을 독립적으로 검증된 증거(테스트 출력·커버리지·린트 결과)에 묶습니다. Go 단일 바이너리로 배포되며 의존성이 없고, 현재 1.2k GitHub 스타 · 222 포크 · 4,456 커밋 규모입니다.

Plan → Run → Sync 3단계

• Plan: GEARS 형식 요구사항으로 SPEC 작성
• Run: TDD(RED→GREEN→REFACTOR) 또는 DDD(ANALYZE→PRESERVE→IMPROVE)
• 자동 선택: 커버리지 10% 초과 또는 신규 프로젝트 → TDD, 커버리지 10% 미만 레거시 → DDD
• Sync: 문서화와 PR 생성

TRUST 5 품질 게이트

• 약어: Tested · Readable · Unified · Secured · Trackable
• 실행: 린트·포맷·타입 검사·테스트를 동시 실행
• 채점 4축: 기능성 40% · 보안 25% · 완성도 20% · 일관성 15%
• 에이전트 12종: 관리자·평가자·빌더·조언자 — 편향 방지를 위한 독립 감사 에이전트 포함

🔗 관련 링크: MoAI-ADK (GitHub) | PyPI | DeepWiki 문서

전망: 「AI가 짠 코드를 어떻게 믿을 것인가」에 대한 답을 프로세스가 아니라 증거 바인딩으로 푸는 접근입니다. 16개 언어(Go·Python·TypeScript·Rust·Java·Kotlin·C#·Ruby·PHP·Elixir·C++·Scala·R·Flutter·Swift·JavaScript)를 우대 없이 동등하게 다루는 점도 특징입니다.

📊 신뢰도 평가:8.0/10
강점: 공식 저장소를 직접 확인해 스타·포크·커밋 수, TRUST 5 채점 가중치, 에이전트 수를 1차 출처에서 수집
개선점: 배포 채널에 따라 서술이 갈린다 — PyPI·DeepWiki 는 「재작업 90% 감소·버그 70% 감소·커버리지 85%+」를 명시하나 README 에는 해당 수치가 없다. 독립 검증되지 않은 벤더 주장으로 취급해야 함

3. TDD의 재부상 — AI 회귀를 막는 몇 안 되는 장치

현황: AI 코딩 도구 채택은 넓어졌지만 신뢰는 오히려 떨어졌습니다. 개발자의 84%가 AI 도구를 쓰거나 쓸 계획이고(2024년 76%에서 상승) 51%가 매일 사용하지만, AI 정확도에 대한 신뢰는 40%에서 29%로 11%p 하락했습니다. 그리고 AI 생성 코드 리뷰가 주당 11.4시간(중앙값)으로 가장 큰 시간 소모가 됐습니다.

품질 지표의 악화

• 버그 증가: 52%가 AI 도입 이후 버그 양이 늘었다고 응답
• PR 결함: AI 공동작성 PR에서 약 1.7배 많은 이슈 발견 (CodeRabbit, 2025-12)
• 코드 중복 4배 증가 · 단기 코드 처닝 상승 — 복붙 증가, 유지보수성 저하
• 그럼에도: 75%는 병합 전 모든 AI 코드를 수동 검토

측정된 처방 — TDAD

• 문제: AI 코딩 에이전트가 기존에 통과하던 테스트를 자주 깨뜨린다
• 방법: 그래프 기반 변경 전 영향 분석
• 결과: 회귀율 6.08% → 1.82% (70% 감소)
• 규모: SWE-bench Verified 100개 인스턴스 (arXiv, 2026)

🔗 관련 링크: TDAD: Test-Driven Agentic Development (arXiv) | CodeRabbit | Stack Overflow Developer Survey

전망: TDD 는 「좋은 습관」에서 「필수 안전장치」로 성격이 바뀌었습니다. 사람이 코드를 다 읽지 못하는 속도로 코드가 생성되는 이상, 테스트가 유일하게 확장 가능한 검증 수단이기 때문입니다.

📊 신뢰도 평가:8.5/10
강점: arXiv 논문의 정량 결과(6.08%→1.82%, N=100)와 복수 설문의 수치를 병기 · 신뢰도 하락(40%→29%)은 전년 대비 비교치
개선점: 설문 수치들의 표본 크기와 조사 주체가 2차 집계 매체를 통해 확인됨 — 원 설문 보고서 대조가 필요

4. DDD가 AI 시대에 오히려 더 중요해졌다

현황: 도메인 주도 설계는 에이전틱 코딩을 「프롬프트 스파게티」에서 유지보수 가능한 공학으로 바꾸는 틀로 재조명받고 있습니다. 핵심 아이디어는 DDD 의 세 도구를 에이전트 설계에 그대로 옮기는 것입니다 — 바운디드 컨텍스트를 에이전트 책임 경계로, 유비쿼터스 언어를 도구 입출력의 일관성 규약으로, 컨텍스트 맵을 통합 지점의 명시적 문서로 씁니다.

멀티 에이전트에 적용하면

• 1 에이전트 = 1 바운디드 컨텍스트: 에이전트가 특정 도메인의 지식과 규칙을 캡슐화
• 예: 재고 관리 에이전트는 재고 상호작용만 전담
• 효과: 책임 경계가 프롬프트가 아니라 구조로 정의됨
• 통합 지점: 컨텍스트 맵으로 명시 — 암묵적 결합 방지

AI가 경계 식별을 돕는다

• 역할: 경계 식별을 대체가 아니라 지원
• 방법: 소스 코드·DB 스키마·상호작용 패턴을 분석해 도메인 응집·분리 신호를 표면화
• 2026년의 실용적 관점: 순수 기술 분석보다 팀 경계와 조직 구조에서 출발할 것
• MoAI-ADK 사례: 커버리지 10% 미만 레거시에 DDD 사이클(ANALYZE-PRESERVE-IMPROVE)을 자동 배정

🔗 관련 링크: DDD matters more when AI writes your code | From Prompt Spaghetti to Bounded Contexts | DDD for Multi-Agent AI Systems

전망: AI 가 코드를 대량 생산할수록 「어디까지가 이 모듈의 책임인가」를 사람이 먼저 정해두는 일의 가치가 올라갑니다. 경계가 없으면 에이전트는 경계를 만들지 않고 가로지릅니다.

📊 신뢰도 평가:7.5/10
강점: 컨퍼런스 발표·실무자 기술 블로그 등 복수 출처가 동일한 매핑(바운디드 컨텍스트=에이전트 경계)을 제시
개선점: 이 영역은 정량 데이터가 부족하고 대부분 설계 담론 — 도입 효과의 수치적 근거는 아직 축적 중

5. 모듈러 모놀리스 회귀 — 이제 제1 제약은 비용이다

현황: CNCF 2026년 1분기 보고에 따르면, 마이크로서비스를 먼저 도입했던 조직의 42%가 일부 서비스를 더 큰 배포 단위로 통합했습니다 — 즉 모듈러 모놀리스로 돌아갔습니다. 2026년 4월 공개된 내부 측정에서는 팩 기반 모듈화 도입 후 신규 개발자 온보딩 시간 55% 감소, 교차 모듈 회귀 전년 대비 68% 감소가 보고됐습니다.

도구 생태계의 성숙

• 2026년 1분기 동시 출시: Spring Modulith 1.4 GA · ArchUnit 1.3 · jMolecules 2026.0
• 의미: 진화적 아키텍처 툴체인이 성숙 단계에 진입
• 적합성 함수(fitness function): 아키텍처 규칙을 테스트로 강제
• 이벤트 소싱: Ecotone·EventSourcingDB 등 프로덕션급 이벤트 저장소 등장

왜 지금 되돌아가나

• 비용이 제1 제약: 2026년 아키텍처 결정의 주된 제약은 확장성이 아니라 비용
• 과잉 적용의 반작용: 엔터프라이즈 프로젝트의 90% 이상은 잘 설계된 모듈러 모놀리스로 충분
• AI가 밀어준다: LLM 통합 애플리케이션·에이전틱 AI 시스템의 부상이 모듈러 모놀리스 회귀를 강화
• AI 진입장벽 완화: 이벤트 소싱 도입이 「수년의 경험」에서 「수주의 가이드 구현」으로

🔗 관련 링크: Spring Modulith | ArchUnit | jMolecules | CNCF

전망: DDD 의 모듈 경계와 모듈러 모놀리스의 배포 단위가 다시 붙습니다. 「경계는 논리적으로, 배포는 하나로」가 2026년의 기본값이 되고 있습니다.

📊 신뢰도 평가:7.0/10
강점: CNCF 분기 보고서라는 업계 표준 출처를 인용 · 도구 릴리스(Spring Modulith 1.4, ArchUnit 1.3)는 검증 가능한 사실
개선점: 온보딩 55%·회귀 68% 감소는 익명 조직의 내부 측정으로 일반화 불가 · 「90% 이상 충분」은 정성 판단

경쟁 환경과 시장 포지셔닝

4계층 시장 구조

사양 주도 개발 도구는 「얼마나 대신 해주는가」와 「결과를 검증하는가」 두 축으로 갈립니다. 계층이 올라갈수록 자동화 범위가 넓어지고, 검증 계층은 그와 별개로 존재합니다.

계층주요 도구특징대상
① 부착형 CLIGitHub Spec Kit, OpenSpec기존 에이전트 위에 얹는 MIT 라이선스 툴킷 · 모델 비종속도구를 직접 고르고 싶은 팀
② 통합 IDEAWS Kiro, Google Antigravity, Cursor사양·모델·과금이 한 울타리 안 · 사양 우선 IDE클라우드 단일 벤더 정착 조직
③ 오케스트레이션 하네스MoAI-ADK, BMAD, Tessl다중 에이전트 조율 · 품질 게이트 · 비용 라우팅품질을 계약으로 다루는 팀
④ 아키텍처 검증ArchUnit, Spring Modulith, jMolecules경계 규칙을 테스트로 강제(적합성 함수)레거시·대규모 코드베이스

주요 시장 변화 5가지

  • 사양이 1차 산출물이 됐다: 코드가 아니라 사양이 버전 관리·리뷰의 대상으로 이동
  • 검증이 차별화 축이 됐다: 「생성」은 상품화됐고, 「생성물을 믿을 근거를 만드는 것」이 경쟁 지점
  • TDD·DDD가 상호 배타가 아니라 조건부 선택: MoAI-ADK 는 커버리지 10%를 기준으로 자동 분기
  • 비용 라우팅이 기능이 됐다: 전략은 상위 모델, 대량 구현은 저가 모델로 나누는 다중 LLM 배분
  • 아키텍처가 다시 수축한다: 마이크로서비스 42% 통합 회귀 — 경계는 유지하되 배포는 합침

주요 도구 비교

📊 신뢰도 평가:7.0/10
강점: 도구별 포지셔닝 서술은 복수 비교 가이드에서 공통 확인 · 42% 통합 수치는 CNCF 출처 명시
개선점: 레이더 차트 점수는 공개 문서를 바탕으로 한 본 분석의 정성 판단이며 벤치마크가 아님

활용 아이디어

시장에서 관찰되는 주요 활용 접근을 소개합니다.

1. 사양 우선 파일럿 - 기능 하나를 골라 사양을 먼저 쓰고 에이전트에 넘겨, 재작업량을 기존 방식과 비교

2. 커버리지 기준 분기 도입 - 신규 모듈은 TDD, 커버리지가 낮은 레거시는 DDD 사이클로 나눠 적용

3. 아키텍처 적합성 함수 배치 - ArchUnit 류로 모듈 경계 규칙을 테스트화해 AI 생성 코드의 경계 위반을 차단

경영진 요약

핵심 발견

  • AI가 코드를 쓸수록 오래된 방법론이 되살아났다: SDD·TDD·DDD 는 유행 회귀가 아니라, 사람이 다 읽을 수 없는 속도로 생성되는 코드를 다루기 위한 필수 장치가 됐습니다.
  • 채택은 넓어졌는데 신뢰는 떨어졌다: 개발자 84%가 AI 도구를 쓰지만 정확도 신뢰는 40%→29%로 하락했고, 리뷰가 주당 11.4시간으로 최대 시간 소모가 됐습니다.
  • 회귀는 측정 가능하고 줄일 수 있다: 그래프 기반 영향 분석으로 AI 에이전트의 테스트 회귀율이 6.08%→1.82%로 감소했습니다(N=100).
  • 검증이 차별화 지점이다: MoAI-ADK 처럼 완료 주장을 증거에 묶는 접근이 등장했습니다 — 「했다」가 아니라 「테스트·커버리지·린트가 그렇다고 말한다」.
  • 아키텍처는 다시 수축 중이다: 마이크로서비스 도입 조직의 42%가 통합으로 선회했고, 비용이 확장성을 제치고 제1 제약이 됐습니다.

상황별 참고

모델·에이전트를 직접 고르고 싶은 팀 → 부착형 CLI(Spec Kit·OpenSpec)
이유: 기존 워크플로 위에 얹을 수 있고 모델에 종속되지 않습니다.
품질을 계약으로 다뤄야 하는 팀 → 오케스트레이션 하네스(MoAI-ADK·BMAD)
이유: 품질 게이트와 독립 감사가 내장돼 「완료」의 정의가 코드로 존재합니다.
레거시 비중이 큰 조직 → DDD 사이클 + 아키텍처 적합성 함수
이유: 커버리지가 낮은 코드에 TDD 를 강제하면 진도가 나가지 않고, 경계 보존이 우선입니다.

종합 평가: 긍정적 (방법론과 도구가 빠르게 성숙 중입니다. 다만 품질 지표는 아직 악화 국면이며, 검증 체계를 갖춘 팀과 그렇지 않은 팀의 격차가 벌어지고 있습니다.)

주요 용어 설명

SDD (사양 주도 개발) - AI 에이전트를 부르기 전에 행동·아키텍처·엣지 케이스·제약을 담은 구조화된 사양을 먼저 쓰는 방식입니다.
TDD (테스트 주도 개발) - 테스트를 먼저 쓰고(RED) 통과시킨 뒤(GREEN) 구조를 다듬는(REFACTOR) 순환입니다.
DDD (도메인 주도 설계) - 업무 도메인의 언어와 경계를 코드 구조에 반영하는 설계 방식입니다. MoAI-ADK 에서는 레거시용 ANALYZE-PRESERVE-IMPROVE 사이클을 가리키기도 합니다.
바운디드 컨텍스트 - 하나의 모델과 용어가 일관되게 통하는 경계. 멀티 에이전트에서는 에이전트 한 개의 책임 범위로 쓰입니다.
유비쿼터스 언어 - 개발자와 도메인 전문가가 같은 뜻으로 쓰는 공통 어휘. 에이전트 도구의 입출력 규약으로도 활용됩니다.
적합성 함수(Fitness Function) - 아키텍처 규칙(예: 모듈 A는 B를 직접 참조 금지)을 자동 테스트로 강제하는 장치입니다.
모듈러 모놀리스 - 내부는 모듈 경계로 나누되 하나의 단위로 배포하는 구조. 마이크로서비스의 운영 비용을 피하면서 경계는 유지합니다.
바이브 코딩(Vibe Coding) - 명세 없이 대화만으로 코드를 만들어내는 방식. 그럴듯하지만 의도에서 표류하는 코드를 낳는다는 문제 제기에서 SDD 가 등장했습니다.
