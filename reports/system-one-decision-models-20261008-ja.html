意思決定モデルの世界動向 —
Jev・Laya と「System One」という範疇ができた3週間

文章を書かずに判定を返すモデル：25種を超える公開クローン、Ollama によるワイヤ形式の標準化、そして2023年の分類器が Jev を上回った初の第三者ベンチマーク
レポート作成日：2026年10月8日 ｜ 詳細版レポート ｜ データ収集：2026-10-08

主要トレンド Top 5

1. Jev —「文章」ではなく「判定」を返すモデル

現状：TypeSafe AI が2026年9月15日に Jev を公開し、自ら「System One モデル」という範疇名を掲げました。大規模言語モデル（LLM）が文章を生成するのに対し、Jev は型の定まった質問に確率つきで答えます。その値をソフトウェアがそのまま条件分岐に使える、というのが要点です。同日 TypeSafe は DCVC 主導の4,000万ドルのシード調達でステルスを解き、Forbes は投資後の企業価値を約2億ドルと報じました。創業者は元 OpenAI 研究者で RLHF・ChatGPT の共同開発者である Diogo Almeida、ほかに Erik Gafni・Sasha Sheng です。

質問の型 3種（プリミティブ）

• Choice：最大255の選択肢から1つ＋選択肢ごとの確率分布
• Score：順序のある評価基準上の位置（2〜10段階）＋段階ごとの分布
• Noul：条件が真である確率（はい・いいえ）
• いずれも信頼度の値を併せて返します
• 学習法は RLCD（Reinforcement Learning for Calibrated Decisions）——「好まれる会話応答」ではなく「判定と使える確率推定」を目標にした事後学習

公式文書に基づく運用仕様

• 版：jev-1.13.0、エンドポイントは POST /v1/systemone
• 文脈長：1リクエスト64kトークン、state＋最長の質問で32k の予算
• 並列評価：state を一度読み、すべての質問を並列に判定
• 料金：入力100万トークンあたり $0.042・出力トークンは無料
• 上限：毎秒10万トークン / 毎秒80リクエスト
• 制約：テキスト専用（画像・音声は非対応）、主たる言語は英語、アカウント別の微調整なし（全顧客で同一の重み）

⚠️ 裏づけの取れない数値が1件：Sequoia のパートナー Pat Grady が「Jev は7日で0 → 売上1億ドル」と述べ、一部の媒体がそのまま掲載しました。本レポートはこの数値を採用しません。同じ時期に公表されたシードは4,000万ドル、投資後の企業価値は約2億ドルであり、シード段階の会社が1週間で1億ドルの売上を立てるなら、その企業価値と両立しがたいためです。TypeSafe は顧客名を1社も公表していません。
📊 信頼性評価： 9/10
強み：仕様・料金・上限・制約は TypeSafe の公式文書（docs.typesafe.ai/models）で、調達の事実は Business Wire の配信原文で確認しました。創業者の経歴も同じ配信文に基づきます。
改善点：パラメータ数・構造・RLCD の詳細は非公開で、「なぜ速いのか」を検証できません。遅延の数値は公式文書にそもそも記載がありません。
🔗 関連リンク： TypeSafe 公式モデル文書 | 4,000万ドル調達の発表（Business Wire） | RLCD の解説（Turing Post）

展望：Jev の本当の発明は、モデルではなくインターフェースである可能性が高いでしょう。「型の定まった3種の質問＋確率」という契約は背後のモデルが何であっても成り立ち、実際に3週間でその契約を実装したモデルが25種を超えました。

2. 3週間のクローン競争 — Laya を含む公開重みが25種以上

現状：Jev 公開の3日後、2026年9月18日に Convai Innovations が Laya の重みを Apache 2.0 で Hugging Face に公開しました。Laya の設計思想は Jev と根本的に異なります。大規模言語モデルを小さくしたものではなく、符号化器（BERT 系）に型判定の出力層を付けた非自己回帰モデルで、文章を生成せず一度の順伝播で答えを出します。英語向けの ModernBERT-large 421M、100以上の言語向けの mmBERT-base 322M、そして文字体系を判別して適切なモデルへ振り分ける振り分け器で構成されます。以後の1か月で、Jev の3種の質問型をそのまま実装した公開モデルが相次ぎました。

Laya の実測仕様（HF モデルカード）

• 構成：421M（英語）/ 322M（多言語）/ 421M（typed-decisions 微調整版）
• ライセンス：Apache 2.0 ・ 実行環境：CPU・CUDA・Apple Silicon
• 遅延：単発で約 33ms、まとめ処理では1問あたり 7.2ms
• 費用：自前のハードウェアならトークン当たり $0（基盤費用のみ）
• 文脈長：英語512 / 多言語1,024トークン —— Jev の64k とは桁が違います
• 学習規模：1,200件（6,000判定）で微調整し、400件（2,000判定）で評価

派生モデルの広がり（一部）

• Decider（Mapika）：Qwen3.5 系の 2B/4B/35B-a3b —— 35B は活性3B・256の振り分け専門家のうち8つが活性
• Nimble（Bespoke Labs）：9B、Qwen3.5-9B の微調整、8,192トークン、選択肢255
• Clef（Cloudflare、10-01）：27B/9B の Apache 2.0、Workers AI、100万トークンあたり $0.09
• Anarkali（ToufiqQureshi）：68M —— 最小の符号化器で、6分の1の規模で Jev を上回ると主張
• AnyJev（Nokia Applied Research）：学習不要 —— 既存 LLM の内部状態を読み、偏りを補正
• Jev-Omni：12B の多モーダル（文章・画像・音声・動画）—— Jev が扱えない領域

📊 信頼性評価： 8/10
強み：Laya の数値は Hugging Face の公式モデルカード（convaiinnovations/laya-typed-decisions）で直接確認しました。学習・評価の件数から業務別の正解率まで一次資料です。
改善点：25種を超える派生モデルの一覧は単一の集約サイトを主な出典としており、個々のリポジトリを全数検証していません。「6分の1の規模で Jev を上回る」といった主張はいずれも公開者自身の評価です。
🔗 関連リンク： Laya（Hugging Face） | laya-typed-decisions モデルカード | Decider（GitHub） | Nimble（Ollama）

展望：このクローン競争の意味は「どれが勝ったか」ではなく、参入障壁が事実上ないことの証明です。68M の符号化器から35B の混合専門家まで、さらには学習がまったく不要な方式（AnyJev・SemIf）まで、同じ契約を満たしてしまいました。

3. ワイヤ形式の標準化 — Ollama が /v1/systemone を搭載した

現状：2026年9月29日、Ollama 0.35 が /v1/systemone エンドポイントを追加しました。重要なのは、これが Jev のワイヤ形式と互換だという点です。商用 API の要求・応答の形式が、わずか2週間で手元の実行環境の標準エンドポイントになったことになります。同日 OpenAI が Decisions API（GPT-6 Luna 系、遅延150ms、限定プレビュー）を、Liquid AI が d1 を投入し、2日後に Cloudflare が Clef を公開しました。範疇が生まれて2週間で、大手基盤事業者3社が参入した形です。

Ollama 0.35（2026-09-29）

• エンドポイント：/v1/systemone —— 入力文・質問・選択肢をまとめて渡します
• 応答：文章ではなく型つきの答え＋確率＋使用量
• 質問の型：choice・noul・score（Jev と同一の名称）
• 当初の搭載モデル3種：Nimble 9B（Bespoke Labs）、Together AI の Tev1 4B と 0.8B（実験版）
• 効果：手元で動かせば追加費用ゼロ＋遅延の低減 —— 問い合わせの振り分け、モデルの経路選択、内容の審査などの用途

同じ週に参入した3社

• OpenAI Decisions API（09-29）：GPT-6 Luna の変種、150ms、限定プレビュー、API 専用
• Liquid AI d1（09-29）：無料枠あり、自社の Jev Decision Index で1位と主張
• Cloudflare Clef（10-01）：Qwen 微調整の 27B/9B、Apache 2.0、Workers AI と自前運用、100万トークンあたり $0.09
• 意味：エッジ（Cloudflare）・最前線（OpenAI）・手元（Ollama）の3経路が同一のインターフェースで同時に開きました

📊 信頼性評価： 8.5/10
強み：Ollama 0.35 のエンドポイント追加と当初搭載の3モデルは複数の独立した報道で一致し、経路名が TypeSafe 公式文書の POST /v1/systemone と同一であることは直接の照合で確認しました。
改善点：OpenAI Decisions API と Liquid AI d1 は限定プレビュー・自社順位に基づくため、一次文書で仕様を確定できていません。「Jev Decision Index で1位」は事業者の主張です。
🔗 関連リンク： Ollama のリリース | Nimble on Ollama | Cloudflare Workers AI | Liquid AI

展望：範疇の勝者はまだ決まっていませんが、インターフェースはすでに決まったように見えます。ワイヤ形式が標準化されればモデルは交換可能な部品になり、競争の軸はモデルの品質より遅延・単価・配置場所へ下がります。これは Jev にとって不利な構図です。

4. 初の第三者ベンチマークによる逆風 — 2023年の DeBERTa 分類器が Jev を上回った

現状：2026年10月2日、Red Hat の開発者ブログが4系統9モデルを同一条件で比較した結果を公開しました。NeMo Guardrails 評価ベンチマークの均衡データセット2件（プロンプトインジェクション、有害性・安全性）で測定しており、結論は明快です——「Jev のような意思決定モデルが、LLM-as-a-judge、事前学習済みの予測モデル、公開の意思決定モデルを、速度でも正解率でも安定して上回ることはない。」

プロンプトインジェクション（正解率 / 遅延）

• Qwen3.6-35B（LLM-as-judge）：89.31% / 312.5ms
• deberta-v3-base-prompt-injection-v2：89.01% / 54.1ms ← 最速
• DiffusionGemma-26B：87.72% / 561.7ms
• Jev-1.13.0：86.35% / 348.1ms
• Laya：85.44% / 119.3ms
• → 2023年系の小さな専用分類器が正解率で2.7ポイント上、遅延は6分の1

内容の安全性（正解率 / 遅延）

• Jev：86.20% ← 1位 / 360.4ms
• DiffusionGemma：85.53% / 499.3ms
• Qwen3.6-35B：85.47% / 307.6ms
• Nemotron-3.5（独自設定）：85.07% / 241.5ms
• granite-guardian-hap-125m：80.27% / 33.2ms
• → Jev は1位ですが、125M のモデルより11倍遅く、差は5.9ポイント

📌 このベンチマークの読み方：著者自身が2点を認めています。① 「LLM-as-a-judge に適した書き方は、ゼロショットの分類器には最適ではない」——実際に Laya は方針文を調整したところ 57.87% → 75.20% へ上がりました（同じモデル、同じデータ）。② GPU クラスタ上のモデルには最低56msの大西洋往復が含まれ、手元の CPU 実行と遅延を直接比べられません。つまりこの表は「モデルの序列」ではなく「初期設定のまま使うと何が起きるか」の記録として読むべきものです。
📊 信頼性評価： 9/10
強み：事業者ではない第三者（Red Hat）が、手法・データセット・モデル版・遅延の測定条件まで公開した唯一の比較です。著者が自らの結果の限界（書き方の未熟さ、通信遅延の混入）を明記している点も信頼を高めます。
改善点：課題が2種類の安全装置に限られ、Jev が売りにする業務判定（問い合わせ振り分け、請求処理）は測定されていません。単回の実行であり、繰り返し測定のばらつきも示されていません。
🔗 関連リンク： Red Hat の第三者ベンチマーク（2026-10-02） | deberta-v3-base-prompt-injection-v2 | NeMo Guardrails

展望：安全装置のように課題が固定され、ラベル付きのデータがある領域では、専用の小型分類器が依然として優位です。意思決定モデルの値打ちはそこではなく、ラベルがなく質問が変わり続ける領域にあります。

5. 本当の争点は正解率ではなく、確率の正直さと汎用性

現状：数値を並べると、この範疇の実際の対立軸が見えてきます。typed-decisions ベンチマークでは 微調整した Laya が正解率0.766 で Jev（0.727）を上回ります。ところが確率のずれ（ECE）は Laya 0.213 対 Jev 0.144 で Jev が優れ、汎用の意図分類 Banking77 では Jev 0.870 対 Laya 0.425 と差が2倍になります。そして決定的なのは Laya のゼロショット正解率が0.362 という点です。つまり Laya は汎用機ではなく専用機です。モデルカード自身が「4つの業務の外では性能が落ちる」と明記しています。

Laya 微調整版の詳細（モデルカード）

• 全体：正解率0.766・soft 0.471・Brier 0.062・ECE 0.213・Score MAE 0.242
• 業務別：請求書処理0.804・セキュリティ事案0.766・顧客対応0.764・エージェント追跡0.730
• 質問型別：noul 0.857・choice 0.733・score 0.723 ← 最も弱い
• 自己申告：「確率分布が過信ぎみ」。温度は学習データで合わせた値なので別データで再調整してから使うことを推奨
• 助言：choice の選択肢は20以下に

なぜ正解率より確率の正直さが大事か

• 実運用の経路選択は信頼度にしきい値を置いて動きます
• したがって「過信する96%のモデル」は「正直な94%のモデル」より実務では劣ります——しきい値が意味を失うためです
• accept/escalate の設計：論文「JEV-as-a-Judge」（arXiv:2609.26550、Li・Miao・Krishnan・Padman）は、確信があるときは自ら確定し、曖昧なときだけ上位の判定者へ渡す構成を評価——しきい値により20〜40%が上位へ回されます
• ただし同論文も「しきい値の調整は課題と領域に依存する」と限界を明記しています

🔍 話題の大きさと実使用量の隔たり：Jev は X で4,000万回表示され、公開クローンは25種を超えました。ところが Laya の typed-decisions 版の月間ダウンロードは722件です（HF モデルカード、2026年10月時点）。さらに Laya が公開した指標はすべて Convai Innovations 自身の評価であり、2026年10月現在第三者の研究機関が再現した例はありません。利用者側の最大の反論もここです——r/LocalLLaMA や Hacker News では 「確率を校正した分類器はすでに解決済みの問題であり、TypeSafe は興味深い主張を検証できるだけの構造を公開していない」という指摘が最も多く出ました。
📊 信頼性評価： 8.5/10
強み：Laya の数値すべてと自己申告（過信、温度の再調整の推奨、選択肢20以下の助言）は公式モデルカードの一次資料で、ダウンロード722件も同じページで確認しました。accept/escalate の構成は arXiv 論文の本文に基づきます。
改善点：Jev の typed-decisions 正解率が出典により 0.727 と 67.8% に分かれます（本文に両方を併記）。このベンチマーク自体が Laya 側が公開した合成業務4種であり、Laya に有利である可能性を排除できていません。
🔗 関連リンク： JEV-as-a-Judge（arXiv:2609.26550） | Laya モデルカード（指標・限界） | Hacker News の議論

展望：この範疇が生き残るなら、勝負は「どれだけ当てるか」ではなく「外れそうなときを自覚できるか」で決まります。確率が文字どおりの意味を持つときにだけ accept/escalate のような設計が成り立ち、そのとき初めて、安価な判定器を前段に置いて高価なモデルを後ろへ回す構成が採算に乗ります。

競争環境と市場ポジショニング

この市場は「どちらが賢いか」で分かれません。重みを配るか、どこで動かすか、汎用か専用かで分かれます。4層すべてが同じ3種の質問型（choice・noul・score）を実装しているため、実務上の選択はモデルの品質よりも配置の制約で決まることが多いのです。

市場で観察される動き

• モデルより先に契約が標準化されました：Jev の /v1/systemone の要求形式が、2週間で Ollama の既定エンドポイントになりました。範疇の歴史としては珍しい速さで、モデルを交換可能な部品に変えます。
• 参入障壁が事実上ないことが証明されました：68M の符号化器（Anarkali）から学習そのものが不要な方式（AnyJev・SemIf）まで、同じ契約を満たしました。独占モデルの防衛線は、ゼロショットの汎用性と確率の正直さだけです。
• 競争の軸が品質から単価・遅延・配置場所へ下がりました：Jev は $0.042/100万（出力無料）、Cloudflare Clef は $0.09/100万、Laya はトークン当たり $0。価格がすでに0に達した層が存在します。
• 第三者の検証が熱を冷ましています：範疇の公開から2週半で出た初の第三者ベンチマークが「安定した優位はない」と結論し、公開された指標はほぼすべて事業者自身の評価です。
• 隣接市場は実在します：LLM の観測・評価基盤市場は2026年の26.9億ドルから2030年に92.6億ドル（年平均成長率36.2%）と見込まれ、LLM-as-a-judge は人による確認より500〜5,000倍安い一方、人の好みとの一致は約80%にとどまります。判定モデルはこの費用曲線をもう一段下げようとする試みです。

活用アイデア

市場で観察される主要な活用アプローチをご紹介します。

1. 既存の分類器と同条件での対照 —— すでに動いている分類箇所を1つ選び、現行方式と判定モデルを同じデータ・同じ測定条件で比べるアプローチ。Red Hat の結果が示したように、専用の小型分類器が勝つ場面は珍しくありません。

2. 確率の正直さを先に測る評価 —— 正解率より先に ECE や Brier を測り、別データで温度を再調整したうえでしきい値を決めるアプローチ。モデルカード自身が過信を認め、再調整を勧めている例があります。

3. accept/escalate の2段構成の設計 —— 安価な判定器を前段に置き、確信のある範囲だけ自ら確定し、曖昧な範囲は上位のモデルか人へ回すアプローチ。公開研究ではしきい値により20〜40%が上位へ回されます。

  • 話題の大きさと実使用量の隔たりを見てください：X の表示4,000万回・クローン25種に対し、Laya の typed-decisions 版の月間ダウンロードは722件で、公開指標はほぼすべて事業者自身の評価です。「7日で売上1億ドル」という主張は公表された企業価値と両立しがたいため、本レポートは採用していません。

Selection Guide

課題が固定され、ラベル付きデータがあるなら → 既存の専用分類器を維持（Tier 4）
理由：同条件で正解率が高く、遅延は6分の1〜11分の1です。新しい範疇へ移る根拠がデータから出てきません。
質問が頻繁に変わり、ラベルがないなら → Jev などホスト型 API（Tier 1）
理由：ゼロショットで使え、64k の文脈で ECE も低いです。ただし重み非公開・データの外部送信・単価変動の危険を抱えます。
データの管轄と費用ゼロが優先なら → Laya などの符号化器系（Tier 3）
理由：CPU で7〜33ms、トークン当たり $0、Apache 2.0。ただし文脈は512〜1,024トークンで、専用機なので自社データで微調整して初めて使い物になります。
長い文脈と世界知識の両方が必要なら → Decider・Nimble・Clef（Tier 2）
理由：LLM 由来なので知識を継承し、文脈も8k以上です。代償は GPU と運用の負担です。

主要用語の説明

意思決定モデル / System One モデル — 文章を生成する代わりに、「選択肢のうちの1つ」「点数」「はい・いいえの確率」のように範囲の定まった答えを返すモデルです。人間の素早い直感的判断（システム1）から取った名前で、ソフトウェアがその値をそのまま条件文に使えることが中心的な主張です。
choice・noul・score — この範疇における3種の質問型です。choice は選択肢から1つを選び（最大255）、noul は条件が真である確率を返し、score は順序のある基準上の段階を返します。Jev が付けた名前がそのまま業界共通の語彙になりました。
確率の校正 / ECE — モデルが「90%の確信」と言うとき、実際に10回のうち9回当たっているかを見る性質です。ECE（期待校正誤差）はそのずれの大きさで、小さいほど確率を信用できます。しきい値で自動処理する仕組みでは、正解率より重要になり得ます。
非自己回帰 — 単語を1つずつ書き足すのではなく、一度の計算で答えを出す方式です。生成しないため格段に速い一方、文章で説明することはできません。Laya が33ms、まとめ処理で7.2ms を出せる理由です。
符号化器モデル（BERT 系） — 文を読んで意味を凝縮することに特化した構造で、文章を書く復号器（GPT 系）と対になります。ModernBERT や DeBERTa がその例で、小さく速い反面、扱える文脈が短いという特徴があります。
RLCD — TypeSafe が Jev に適用したと述べている事後学習で、「人が好む返答」ではなく「正しい判定と使える確率」を報酬にします。対話モデルの RLHF とは目標が違うという主張ですが、詳しい方法は公開されていません。
LLM-as-a-judge — 大きな言語モデルに、他のモデルの出力や利用者の入力を評価させる方式です。人による確認より数百〜数千倍安い一方、人の好みとの一致は約80%にとどまり、応答を生成するため遅いという弱点があります。意思決定モデルが置き換えを狙っているのは、まさにこの位置です。
安全装置（ガードレール）/ プロンプトインジェクション — 安全装置は AI の入出力を方針に沿って選り分ける仕組みで、プロンプトインジェクションは悪意ある入力でモデルへの指示を乗っ取る攻撃です。Red Hat のベンチマークが測った2つの課題がこの領域です。
accept/escalate — 確信が高いときは自ら確定し、曖昧なときだけ上位のモデルか人へ渡す2段構成です。安価な判定器を前に置いて全体の費用を下げる設計であり、確率が正直であるときにだけ成り立ちます。
